# Техническое задание: «По счетам»

Версия 1.0 · 25 сентября 2026 года

Назначение: закрытый семейный сайт для планирования регулярных месячных обязательств и распределения денег по счетам.

## 1. Цель и границы

Семья получает деньги из разных источников на разные счета и распределяет их между регулярными платежами, повседневной жизнью и накоплениями. Зарплата, доход от деятельности, 800+, доход жены и другие поступления — равноправные настраиваемые источники. Бизнес-счёт и обязательства ИП не являются обязательной частью модели. Приложение должно отвечать на вопросы:

1. Сколько денег потребуется на постоянные платежи выбранного месяца?
2. Сколько оставить на каждом счёте для запланированных платежей?
3. Сколько, откуда и куда перевести с учётом доступных денег и разных поступлений?
4. Сколько выделить на повседневную жизнь и накопления?
5. Сколько останется свободно для расходов вне списка?

Это план денежных средств, а не учёт фактических расходов. Пользователи не должны записывать покупки или сверять транзакции в течение месяца. Переводы выполняются вручную в банковских приложениях; сайт не получает банковские полномочия и не отправляет деньги.

## 2. Подтверждённые решения и принятые допущения

### 2.1. Подтверждено пользователем

| Вопрос | Решение |
|---|---|
| Пользователи | Два члена семьи |
| Доступ | Google; только два разрешённых аккаунта |
| Права | Оба видят все данные, включая доход, и могут редактировать |
| Данные | Один общий семейный набор данных; не два независимых бюджета |
| Доходы и суммы платежей | Ручной ввод каждый месяц; произвольные источники и категории |
| Расходы | Регулярные (каждый месяц или по дням недели) и разовые в конкретном месяце; могут появляться, исчезать и менять сумму |
| Исключения | В отдельном месяце платёж может отсутствовать |
| Разовые платежи | Добавляются внутри открытого месяца и не переходят в следующий. Учёт повседневных покупок не ведётся |
| Основной результат | Список переводов, бюджет на жизнь, накопления, свободный остаток |
| Гибкость | Никаких обязательных категорий ИП; несколько источников дохода, включая 800+ |

### 2.2. Допущения для первой версии

Следующие решения предлагаются как реализация первой версии, а не как ранее подтверждённые пожелания:

- Русский интерфейс, PLN, суммы с точностью до 0,01 zł, часовой пояс Europe/Warsaw.
- Произвольное число счетов, карт, наличных кошельков и накопительных счетов. Можно выбрать один или несколько счетов-источников переводов и их приоритет. Для начала достаточно одного; бизнес-статус счёта на формулы не влияет.
- Планирование на календарный месяц; фиксируется дата, на которую введены остатки. Если деньги распределяются за следующий месяц, пользователь выбирает этот месяц явно.
- Работа онлайн с телефона и компьютера. Офлайн-редактирование не входит в первую версию.
- В первой версии нет автоматического расчёта налогов, банковских интеграций, чтения Google Sheets и валютной конвертации.
- Первичное заполнение справочника вручную. Существующая таблица — ориентир по структуре, а не источник актуальных сумм по умолчанию.
- Оба пользователя редактируют бюджет; изменение списка разрешённых Google-аккаунтов выполняется отдельно через защищённую конфигурацию сервера.

## 3. Основные сценарии

### 3.1. Первичная настройка

1. Развёртывание приложения с двумя разрешёнными Google-идентичностями.
2. Создание общего семейного пространства и вход первого пользователя.
3. Добавление счетов: название, тип, порядок отображения. Реальные номера карт, IBAN и банковские пароли не нужны.
4. Выбор счетов, с которых разрешено предлагать переводы, и их порядка. По умолчанию достаточно одного выбранного основного счёта.
5. Создание справочников регулярных платежей и доходов с базовыми суммами и счетами списания/зачисления.
6. Создание первого месячного плана.

### 3.2. Планирование месяца

1. Пользователь нажимает «Создать месяц» и выбирает год и месяц.
2. Система создаёт независимый снимок действующих базовых платежей и доходов.
3. Пользователь вводит доступные остатки на выбранную дату и подтверждает ещё ожидаемые поступления: зарплату, 800+, доход жены и любые другие источники.
4. Проверяет платежи: меняет сумму, количество занятий, счёт или исключает платёж только на этот месяц.
5. Задаёт бюджет на жизнь и сумму накоплений, выбирает счета назначения.
6. Видит рассчитанный список переводов и предупреждения о нехватке денег.
7. Выполняет переводы в банковских приложениях. Вносить последующие покупки не требуется.
8. При необходимости фиксирует план, чтобы защитить его от случайных изменений.

### 3.3. Работа вдвоём

Изменение, сохранённое одним пользователем, доступно второму. Интерфейс показывает время последнего сохранения и автора последнего изменения. Одновременное редактирование не должно приводить к незаметной потере данных.

## 4. Структура интерфейса

Актуальная структура — три раздела «Месяц», «История», «Настройки»; сценарии и экраны описаны в [user-journeys.md](user-journeys.md). Подразделы ниже — исходные требования; где они расходятся со сценариями, действуют сценарии.

### 4.1. Вход

- Название приложения и кнопка «Войти через Google».
- До успешной авторизации не отображаются финансовые данные, имена владельцев, список разрешённых email и название семейного пространства.
- Постороннему аккаунту показывается нейтральное «Доступ не предоставлен» и возможность выбрать другой Google-аккаунт.

### 4.2. «План месяца» — главный экран

Состав:

1. Выбор месяца и состояние плана: «Черновик» / «Зафиксирован».
2. Главный показатель: «Свободно после распределения»; отрицательное значение — «Не хватает».
3. Доходы, постоянные платежи, бюджет на жизнь и накопления отдельными суммами. Любую пользовательскую категорию можно раскрыть для детализации.
4. Блок «Переводы»: откуда → куда, сумма, условие доступности денег. У каждого счёта — потребность, доступный остаток, ожидаемые поступления и итоговое пополнение.
5. «Останется на счетах»: сколько предназначено для платежей, жизни и накоплений и сколько свободно на каждом счёте.
6. Блок исходных данных: остатки, источники доходов, платежи, бюджет на жизнь и накопления.
7. Ссылки на редактирование платежей и детализацию расчётов.

На телефоне сначала показываются свободный остаток и переводы, затем исходные данные. Большие таблицы заменяются карточками. Не должно быть необходимости двигать страницу горизонтально.

### 4.3. «Платежи месяца»

- Название, плановая сумма, счёт, срок, переключатель «Включён в этом месяце».
- Для платежей по количеству: цена единицы и плановое количество; итог рассчитывается автоматически.
- Выключенный платёж остаётся видимым и не участвует ни в общей сумме, ни в суммах по счетам.
- Действие «Вернуть базовые значения» доступно для отдельного платежа.
- При изменении понятный выбор области: «Только этот месяц» или отдельное действие «Изменить базовый платёж с месяца…».
- Добавление новой регулярной статьи возможно прямо отсюда через форму с месяцем начала действия.
- Нет обязательных полей «Оплачено», «Фактически потрачено» и ежедневного журнала операций.

### 4.4. «Регулярные платежи»

Справочник с базовой суммой/расчётом, счётом списания, сроком оплаты, первым и последним месяцем действия. Добавление, изменение, завершение действия и архивирование. Архивные статьи доступны для просмотра.

### 4.5. «Счета»

Настройка счетов и их порядка. Бизнес- и личный счета одного банка имеют разные названия, например «Банк А · бизнес» и «Банк А · личный». Аккаунты входа и банковские счета — разные сущности.

### 4.6. «Доходы»

Произвольные источники: зарплата, 800+, доход жены, подработка и другие. У каждого — название, сумма/оценка, счёт зачисления, ожидаемая дата и включение в месяц. Регулярный источник имеет базовый шаблон; нерегулярное поступление можно добавить только в текущий план. Пауза или изменение суммы действует только в выбранном месяце, если пользователь явно не меняет шаблон. Источник может быть выключен без удаления истории.

### 4.7. «История»

Список месячных планов с основными итогами. Открытие выбранного месяца, просмотр, фиксация и явное возвращение к редактированию. Отдельная история изменений показывает автора, время, объект и старое/новое значение; она доступна только двум пользователям приложения.

## 5. Правила регулярных платежей и месяцев

### 5.1. Базовые значения и месячные исключения

Базовый платёж — шаблон для создания месяца. Платёж месяца — самостоятельная запись со снимком названия, суммы, способа расчёта, счёта и срока.

| Действие | Поведение |
|---|---|
| Изменить сумму в месяце | Меняется только выбранный план |
| Пропустить платёж | Выключается только выбранный месяц |
| Изменить базовую цену с ноября | Новые планы с ноября используют новую цену |
| Завершить платёж после октября | В новые планы с ноября не добавляется |
| Добавить новый платёж с ноября | Добавляется при создании планов начиная с ноября |
| Переименовать/архивировать счёт | Старые планы сохраняют своё название и ссылки |

Уже созданные планы, включая будущие черновики, автоматически не переписываются. Исключение — открытый месяц: изменения настроек сразу попадают в него, но значения, изменённые в самом месяце, и месячные исключения сохраняются. У зафиксированного плана эта операция недоступна. Сравнение идёт с версиями шаблонов, действующими для этого месяца; по каждому пункту видно «было → станет», по умолчанию отмечены все пункты. Для платежа по дням недели исправленное вручную количество сохраняется, пока не поменялись дни недели. Статус получения дохода не меняется.

При создании нового месяца берутся версии шаблонов, действующие для этого месяца. Поэтому временный пропуск бассейна или уменьшенное количество занятий не наследуются из предыдущего плана.

### 5.2. Создание и сохранение

- В одном семейном пространстве один план на пару год/месяц. Двойной клик или повтор запроса не создаёт дубликат.
- Текущие остатки и отметки о получении доходов в новый месяц не переносятся. Регулярные доходы создаются из базовых шаблонов как ожидаемые; суммы нужно подтвердить. Месячные изменения прошлого плана не наследуются.
- Бюджет на жизнь и накопления можно предложить из предыдущего плана как несохранённые значения с явным подтверждением.
- Незаполненная сумма отличается от нулевой. Пока обязательные исходные данные не подтверждены, итог помечен «Предварительный»; нельзя показывать уверенное «Всё распределено».
- Сохранение формы явно показывает состояния «Сохранение», «Сохранено», «Не удалось сохранить». При ошибке введённые значения не исчезают.
- Открыт всегда не больше одного месяца. «Закрыть месяц» (с подтверждением) делает его доступным только для просмотра. Открыть снова можно только последний месяц и только пока следующий не начат; повторное открытие журналируется. Следующий месяц начинается кнопкой «Начать <месяц>» и собирается из текущих настроек.
- Удаление черновика требует подтверждения. Зафиксированный план нельзя незаметно удалить или переписать.

### 5.3. Расчёт платежа

Расписание регулярного платежа:

1. **Каждый месяц** — фиксированная сумма, необязательный день месяца.
2. **По дням недели** — цена за один раз и дни недели (например, пн и чт). При создании месяца количество = число этих дней в месяце, сумма = цена × количество. Количество можно поправить в месяце (праздник, пропуск).

Разовый платёж создаётся только внутри открытого месяца и не связан со справочником. Заранее на будущие месяцы разовые платежи не планируются. Более редкие периоды (раз в квартал, раз в год) в первую версию не входят.

Исключение платежа из месяца — явное действие с необязательной причиной («уже оплачено», «не нужно в этом месяце»). Исключённые платежи показываются отдельной группой и не входят в суммы. На странице месяца добавляются только разовые платежи; регулярные заводятся в справочнике.

Режимы суммы:

1. Фиксированная сумма.
2. Цена единицы × количество, например 70 zł × 3 занятия = 210 zł.

В первой версии количество — целое неотрицательное число. Ноль допустим. Отрицательные цены и количества запрещены. Сумма выключенного платежа сохраняется для удобства, но его вклад в расчёт равен нулю. Изменения поступают на сервер атомарно вместе с проверкой версии.

Те же правила версий, сроков действия, месячных исключений и снимков применяются к регулярным источникам дохода. Отключённые источники не участвуют в суммах. При смене счёта зачисления прошлые планы сохраняют первоначальный счёт.

### 5.4. Срок оплаты

Поддержать день месяца и «В течение месяца». Для дня 29–31 в коротком месяце использовать последний календарный день. Сроки служат подсказкой и для проверки будущих поступлений, а не для учёта фактической оплаты.

## 6. Универсальная финансовая модель и расчёты

### 6.1. Счета, категории и источники

- Все счета имеют одинаковое поведение в формулах. «Бизнес», «личный», «карта», «наличные», «накопительный» — описательные типы.
- Источник дохода не равен счёту. Несколько доходов могут приходить на один счёт; доходы супругов входят в общий план.
- Любая сумма, которую нужно оплатить или выделить, привязана к конкретному счёту.
- Категории платежей настраиваются: жильё, дети, подписки, налоги, услуги и т. п. Можно создавать, переименовывать и архивировать категории; расчёты не зависят от их названий.
- PIT, VAT, ZUS и бухгалтер при необходимости создаются как обычные регулярные платежи с выбранной категорией и счётом. Их наличие не обязательно; ставки и формулы налогов не зашиты в приложение.
- Перемещение между своими счетами — перевод, а не новый доход или расход. Одна сумма не должна появляться в обоих местах.

### 6.2. Начальные остатки и доходы без двойного учёта

У плана есть единая дата исходных остатков. Остаток — сумма, доступная для этого плана, без неприкосновенных накоплений и денег, зарезервированных для другого периода.

1. Уже полученная к этой дате зарплата или 800+ включена в остаток своего счёта. Повторно прибавлять её нельзя.
2. В финансирование добавляются только доходы со статусом «Ещё ожидается». У записи есть название, сумма, счёт, ожидаемая дата.
3. Регулярный доход, уже включённый в исходный остаток, может оставаться видимым со статусом «Учтён в остатке»; его дополнительный вклад равен нулю. Статус должен явно пояснять это поведение.
4. Создание месячного плана не угадывает, пришла ли зарплата. Пользователь подтверждает статус предложенных источников. При неподтверждённых доходах итог помечен предварительным.
5. Если пользователь хочет обновить план после поступления денег, действие «Учесть поступление в остатке» атомарно увеличивает остаток соответствующего счёта на фактически полученную сумму и переводит доход в статус «Учтён в остатке». Пользователь не должен одновременно вручную включить ту же сумму в остаток. Изменение фиксируется в истории; повтор операции не прибавляет деньги вновь.
6. Альтернатива — единое действие «Обновить исходные данные»: новая дата, новые остатки и пересмотр статусов доходов/оставшихся платежей с предварительным сравнением итогов. Простого скрытого повторного начисления нет.
7. Сайт можно вообще не обновлять после распределения: основное назначение — сохранённый план на момент расчёта, не текущий банковский баланс.
8. Включённые платежи должны отражать ещё нуждающиеся в финансировании суммы на дату плана. Если пользователь начинает план после оплаты аренды и вводит остаток после оплаты, аренду нельзя вычесть снова: исключить из этого распределения с пояснением «Уже покрыто до даты плана». Это необязательная разовая корректировка, а не журнал покупок.

Отчёт «Доходы» показывает ожидаемое и учтённое в остатках отдельно. Показатель «Всего доступно для плана» не является показателем месячного заработка: он включает переходящие остатки.

### 6.3. Бюджет на жизнь и накопления

Повседневная жизнь — одна плановая сумма или несколько сумм по счетам, без детализации покупок. Накопления — отдельная плановая сумма с выбранным счётом. Старый неприкосновенный запас накоплений не считается свободными деньгами.

На одном счёте могут одновременно находиться средства для платежей, жизни и новых накоплений. Они складываются в единую потребность, а доступный остаток вычитается один раз. Назначение суммы сохраняется, даже если физического перевода не требуется. Бюджет на жизнь покрывает расходы вне справочника регулярных платежей.

### 6.4. Основные формулы

Для каждого счёта `a`:

- `A_a` — доступный исходный остаток.
- `I_a` — сумма включённых, ещё ожидаемых поступлений.
- `P_a` — включённые постоянные платежи с этого счёта.
- `L_a` — бюджет на жизнь, выделяемый на этот счёт.
- `S_a` — сумма новых накоплений, выделяемая на этот счёт.

```text
Средства счёта V_a = A_a + I_a
Потребность N_a = P_a + L_a + S_a
Необходимое пополнение D_a = max(0, N_a − V_a)
Свободно до переводов E_a = max(0, V_a − N_a)

Всего доступно V = сумма V_a
Все постоянные платежи P = сумма P_a
Свободно после распределения F = сумма V_a − сумма N_a
Контрольное равенство: F = сумма E_a − сумма D_a
```

Переводы не вычитаются из `F`: деньги остаются внутри семейного плана. Отрицательный `F` означает общий дефицит. Положительный `F` не гарантирует доступность денег на нужном счёте и в нужный день.

### 6.5. Составление списка переводов

Пользователь выбирает разрешённые счета-источники и их приоритет. Можно использовать только один источник, например основной счёт получения дохода. Приложение не требует наличия бизнес-счёта.

Алгоритм для первой версии:

1. Рассчитать `N_a`, `D_a`, `E_a` для всех активных счетов.
2. Счёт может отдавать только свой избыток `E_a`, после обеспечения собственных платежей, жизни и накоплений.
3. В порядке приоритета источников распределять их избытки на счета с дефицитом. Получатели упорядочены по раннему известному сроку платежа, затем по пользовательскому порядку и ID для стабильного результата.
4. Сумма одного перевода — минимум оставшегося избытка источника и оставшегося дефицита получателя. Остатки изменяются только внутри расчёта; исходные данные не переписываются.
5. Объединять суммы для одной пары «откуда → куда». Не создавать переводы самому себе, нулевые строки или цепочки через промежуточный счёт.
6. Показывать сумму переводов, непокрытые дефициты и свободные остатки по счетам после предложенных переводов.
7. Если денег в выбранных источниках недостаточно, не списывать автоматически средства с остальных счетов. Показать непокрытую сумму и имеющийся избыток на неразрешённых источниках; пользователь может изменить настройки.

Для счёта после предложенных переводов:

```text
Расчётные средства после переводов = V_a + входящие переводы − исходящие переводы
Свободно на счёте = расчётные средства после переводов − N_a
```

Сумма свободных остатков по всем счетам, включая отрицательные непокрытые значения, равна `F`. Названия «оставить для платежей» и «свободно» должны быть различимы. Список переводов — рекомендации, а не реальные банковские операции.

### 6.6. Доступность денег по времени

- Если перевод зависит от будущего дохода, он не отображается как безусловно доступный сегодня. Показывается условие «После поступления …».
- Если ожидаемый доход поступает позже срока платежа, показывается предупреждение о возможной временной нехватке.
- Для первой версии достаточно консервативной проверки известных дат по счетам. При наличии будущих доходов и платежей без точной даты показывать «Проверь сроки поступлений перед переводами»; не заявлять полную проверку платёжеспособности по дням.
- Алгоритм выше рассчитывает месячное распределение, а не оптимальный ежедневный график переводов. Автоматическое внутримесячное кредитование и цепочки возвратных переводов не входят в первую версию.
- Нехватка денег обозначается текстом и суммой. Отрицательные суммы не обрезаются до нуля в показателе общего свободного остатка.

### 6.7. Точность и проверяемость

Все расчёты ведутся в грошах или decimal. Сервер — окончательный источник итогов. Фильтрация и сортировка строк не влияют на суммы. Выключенная статья не участвует ни в общей сумме, ни в сумме по счёту. Повторное выполнение расчёта при одинаковых данных даёт одинаковый список переводов.

### 6.8. Контрольный пример — тестовые данные

| Параметр | Значение |
|---|---:|
| Ещё ожидаемый доход на основной счёт | 12 000,00 zł |
| Постоянные платежи с основного счёта | 3 000,00 zł |
| Платежи со счёта для платежей | 4 000,00 zł |
| Платежи с дополнительной карты | 800,00 zł |
| Уже доступно на счёте для платежей | 200,00 zł |
| Ещё ожидаемый доход на счёт для платежей | 1 000,00 zł |
| Уже доступно на дополнительной карте | 100,00 zł |
| Жизнь на отдельную карту | 2 000,00 zł |
| Накопления на отдельный счёт | 1 500,00 zł |

Исходные остатки основного счёта, карты для жизни и накопительного счёта равны нулю. Источник переводов — основной счёт. Поступления планируются до необходимых платежей.

Всего постоянных платежей — 7 800,00 zł. После ожидаемого дохода оставить на основном счёте 3 000,00 zł для его платежей; перевести на счёт для платежей 2 800,00 zł, на дополнительную карту 700,00 zł, на жизнь 2 000,00 zł, в накопления 1 500,00 zł. Всего переводов 7 000,00 zł. Свободно после распределения — 2 000,00 zł. До поступления дохода переводы помечены условными. Это полностью вымышленный пример, не отражающий бюджет семьи.

## 7. Совместная работа и целостность данных

- Каждая изменяемая сущность имеет номер версии и время последнего изменения.
- При записи сервер проверяет ожидаемую версию. Если один пользователь сохранил новую версию раньше, сохранение старой версии вторым отклоняется с понятным сообщением и показом актуальных данных. Введённые им значения сохраняются в форме для сравнения.
- Запрещено молча сохранять весь устаревший план поверх изменений другого человека.
- После сохранения пересчитываются все связанные итоги одной согласованной версии плана.
- После возврата во вкладку браузера данные обновляются. Пока экран открыт, изменения второго пользователя появляются не позже чем через 30 секунд; допустим опрос сервера.
- Финансовая история изменений хранится в защищённой БД. В технические логи зарплаты и значения платежей не попадают.
- Повтор создания плана и повтор сохранения после сетевого сбоя не дублируют сущности.

## 8. Безопасность и приватность — обязательные условия выпуска

### 8.1. Модель доступа

Вход через Google устанавливает личность. Отдельная серверная проверка решает, разрешён ли этой личности доступ к семейным данным. Сам по себе успешный вход в любой Google-аккаунт доступа не даёт.

`SEC-01`. Список ровно двух разрешённых пользователей хранится на сервере; клиент не может добавить себя или изменить разрешения. По умолчанию доступ запрещён. Все API чтения, записи, истории и экспорта проверяют активную сессию, членство в единственном семейном пространстве и принадлежность запрашиваемого объекта. [1]

`SEC-02`. Google ID token проверяется на сервере готовой поддерживаемой библиотекой: подпись, issuer, audience, срок действия и предусмотренные выбранным OIDC-потоком проверки. Для серверного потока использовать Authorization Code с PKCE, проверками state и nonce. Redirect URI фиксированный, HTTPS; произвольные внешние адреса возврата не принимаются. [2]

`SEC-03`. Устойчивая идентичность пользователя — проверенный Google `sub`, а не email из формы или frontend. При начальном подключении используется заранее заданный email и подтверждённая сервером личность, затем сохраняется привязка к `sub`. Для Google-аккаунта с внешним почтовым адресом, не обслуживаемым Google, email-only автодопуск не используется: привязка `sub` подтверждается владельцем через защищённую серверную настройку. После привязки другой `sub` с похожим адресом не допускается. [2]

`SEC-04`. Публичной регистрации, приглашений по ссылке и создания новых семейных пространств нет. Попытка входа постороннего человека не создаёт ему финансовый профиль и не открывает никаких данных.

### 8.2. Сессии

`SEC-05`. Использовать серверные отзываемые сессии. Идентификатор сессии — в cookie `Secure`, `HttpOnly`, `SameSite=Lax`, с ограничением на host; не в localStorage и не в URL. Финансовые данные не хранить постоянно в localStorage, IndexedDB или офлайн-кеше. [3]

`SEC-06`. Срок сессии по умолчанию: до 7 суток с момента входа, с завершением после 24 часов без активности. Это продуктовые значения первой версии, настраиваемые на сервере. Выход уничтожает серверную сессию и очищает клиентское состояние. Повторный вход обновляет идентификатор сессии. Удаление аккаунта из разрешённого списка прекращает доступ при следующем запросе независимо от срока cookie.

`SEC-07`. Записи защищены от CSRF токеном и проверкой Origin. SameSite — дополнительная защита, а не единственная. GET-запросы не изменяют финансовые данные. [3, 4]

### 8.3. Приложение и инфраструктура

`SEC-08`. HTTPS обязателен для production. База данных доступна только серверному приложению и обслуживающей инфраструктуре. Ключи, Google client secret и пароли БД находятся в серверном хранилище секретов, не в репозитории, frontend bundle или публичной конфигурации.

`SEC-09`. Все входные данные проверяются на сервере: суммы, длины строк, даты, идентификаторы счетов и версионность. Текст названий выводится экранированным; пользовательский HTML не исполняется. Для БД используются параметризованные запросы/ORM. Ошибки не показывают stack trace, SQL, токены и финансовые данные.

`SEC-10`. Приватные ответы используют `Cache-Control: no-store`. Нельзя помещать зарплаты и платежи в публичные HTML-файлы, исходный код, статические JSON, URL, source maps или публичные демоданные. При выходе, истечении сессии и восстановлении страницы из истории доступ проверяется повторно до показа приватного содержимого.

`SEC-11`. Настроить CSP с минимально необходимыми источниками, запрет встраивания чужими сайтами через `frame-ancestors`, `X-Content-Type-Options`, ограничительную Referrer-Policy и HSTS для production. Разрешения под фактически выбранный Google login flow тестируются отдельно.

`SEC-12`. Ограничить частоту запросов входа и API. При отзыве разрешения или сбое проверки авторизации система закрывает доступ, а не пропускает пользователя.

`SEC-13`. Не подключать рекламные SDK, запись пользовательских сессий и аналитику, собирающую содержимое экранов. В мониторинг ошибок не отправлять тела финансовых запросов, токены, cookie, суммы и экспортируемые данные. Минимальные технические логи — идентификатор события, псевдонимизированный ID пользователя, тип операции, время и результат.

`SEC-14`. Шифрование БД на стороне хранилища; секреты отдельно от выгрузок. Dev/test/preview используют синтетические данные и отдельные секреты. Реальные данные не копируются в публичный preview. Резервное копирование отложено отдельным решением владельца.

`SEC-15`. Использовать поддерживаемые версии зависимостей; перед выпуском проверять уязвимости и не оставлять известные применимые критические/высокие уязвимости без устранения.

### 8.4. Границы защиты

Приложение защищает данные от неавторизованного доступа к сайту и API. В первой версии это не end-to-end encryption: администратор серверной инфраструктуры с соответствующими правами технически может читать БД. Настройка инфраструктуры должна свести такие права к необходимому минимуму. Пользователям рекомендуется включить двухэтапную защиту Google-аккаунтов; сайт не заявляет, что способен самостоятельно подтвердить её включение.

Скрытый адрес сайта, robots.txt и отсутствие ссылок в поиске не считаются защитой. Обещание абсолютной недоступности данных при взломанном телефоне или Google-аккаунте не входит в модель безопасности.

## 9. Хранение и резервные копии

- Основное хранилище — серверная реляционная БД с транзакциями и миграциями.
- Резервное копирование и проверка восстановления отложены отдельным решением владельца; до их внедрения гарантии по сроку восстановления и допустимой потере данных не заявляются.
- Импорт резервной копии через UI не планируется в первой версии; административную процедуру восстановления определить при добавлении резервного копирования.
- Сохранённые месяцы хранятся до явного удаления пользователями. Технические логи — 30 дней, история изменений бюджета — вместе с соответствующими данными.
- Для удаления всей семьи потребуется отдельная защищённая административная процедура.

## 10. Предлагаемая архитектура и модель данных

Архитектура: адаптивный SPA-интерфейс, серверный API/BFF, серверная Google-аутентификация, реляционная БД. SPA не должна обращаться к БД с привилегированным ключом. Для двух человек достаточно одного серверного приложения; микросервисы не требуются.

Принятый стек: React + TypeScript в Next.js, серверные маршруты `/api`, отдельный PostgreSQL-проект Supabase и отдельный Vercel-проект; UI и API на одном origin. .NET не используется. Серверный контроль доступа обязателен.

Идентификатор семьи определяется сервером из разрешённого пользователя, а не принимается на доверии из запроса.

- Локальный предварительный пересчёт до 100 мс для 200 платежей; подтверждение сервером в нормальных условиях до 1 секунды, без учёта нестабильной сети и Google login.
- При загрузке и сетевой ошибке старые числа не выдаются за свежие. Показывается время актуальности.
- Демоданные отделены от production. Мокап служит ориентиром структуры, но не источником авторитетных расчётов или настроек безопасности.

## 13. Состав первой версии и дальнейшие возможности

Обязательный MVP: два Google-аккаунта; общий бюджет; счета; версии регулярных платежей; месячные снимки и исключения; произвольные источники доходов и их шаблоны; ручные исходные данные; бюджет жизни и накопления; переводы из одного или нескольких разрешённых источников и расчёт дефицита; история месяцев; защита от конфликтов; журнал изменений; фиксация плана; JSON-экспорт; адаптивный UI; проверки безопасности. Резервные копии — отдельный будущий этап.

Вне MVP: банковские подключения и реальные переводы; отслеживание покупок; автоматическое налогообложение; Google Sheets import/sync; несколько валют; инвестиционный учёт; оптимизация ежедневного графика межбанковских перемещений; офлайн-режим; дополнительные семьи и пользователи; push-уведомления.

Опционально после использования первой версии: отметки выполненных переводов с корректным учётом уже отправленных сумм; сценарии «что если»; экспорт в XLSX; более подробный календарь поступлений и платежей. Эти возможности не должны усложнять первый релиз.

## 14. Что требуется перед развёртыванием

Для проектирования дополнительная информация не обязательна. Перед настройкой production потребуются:

1. Два разрешённых Google-аккаунта и безопасная привязка их `sub`.
2. Домен, хостинг приложения и БД, бюджет на обслуживание, владелец инфраструктуры.
3. Фактический список счетов, доходов и выбор разрешённых источников переводов.
4. Актуальные базовые платежи, первый месяц и исходные суммы; старые строки таблицы не считать автоматически актуальными.

Комплект результата реализации: исходный код, миграции БД, инструкция развёртывания и обновления, описание секретов без их значений, процедура изменения двух разрешённых пользователей, автоматические тесты. Инструкция резервного копирования и восстановления будет добавлена на отдельном этапе. Публичное размещение реальных финансовых данных для демонстрации не допускается.

## 15. Основания и технические источники

Продуктовые требования основаны на обсуждении с пользователем 25.09.2026, просмотре структуры таблицы «Учёт финансов (с 2026)» и интерактивном мокапе. Часть платежей из таблицы использована для контрольного примера; доходы и остатки в §6.8 — демонстрационные, а весь пример не является актуальным финансовым планом семьи. Технические источники проверены 25.09.2026; конкретные настройки выше являются требованиями проекта.

1. [OWASP — Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): запрет по умолчанию и проверка разрешений для каждого запроса.
2. [Google — Verify the Google ID token on your server side](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) и [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect): серверная проверка токена, идентичность по sub, ограничения доверия к email.
3. [OWASP — Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): защита cookie, управление сессиями и дополнительная роль SameSite.
4. [OWASP — CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): защита изменяющих запросов.
